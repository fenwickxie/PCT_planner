# PCT-Planner 论文原理中文解读

> 本文是基于仓库附带论文整理的原创中文概述与技术解释，不是论文全文翻译，也不替代原文。论文题为 *Efficient Global Navigational Planning in 3D Structures based on Point Cloud Tomography*，发表于 IEEE/ASME Transactions on Mechatronics（2024）；原文见本目录 PDF。下文尽量用自己的表述梳理问题、方法和实现关系。

## 1. 一句话理解

PCT-Planner 不把机器人必须搜索的空间表示成完整三维体素，而是沿高度方向叠放多张二维“切片地图”。每张切片都描述某个高度附近的地面、其上方的顶棚及通行代价；跨层转换由 gateway 连接。这样保留多层结构和地形细节，同时把大部分地图处理与路径搜索留在高效的二维网格上。

## 2. 论文要解决的矛盾

地面机器人在室内多层、坡道、桥面、树冠/顶棚下行驶时，需要同时判断“脚下能不能走”和“上方有没有碰撞”。常见表示各有代价：

- 原始点云细节充足，但无序，不利于规则的全局搜索和快速碰撞/地形查询。
- 单层高程图高效，却无法在同一 XY 位置区分上下重叠的两块地面。
- 多层列表或完整体素图可以表达结构，但场景评估、存储和轨迹搜索开销可能随场景规模快速上升。

论文的核心选择是把环境约化为一组有序的 2.5D 切片地图：每个 XY 网格仍只需保存少量有明确含义的通道，而不是完整的 XYZ 占据体。

## 3. 从点云构造 tomogram

### 3.1 高度平面与投影

先在 Z 方向按固定间距布置水平平面。对某一平面和某个 XY 格子：

- 将平面下方落入该格子的点视为地面候选，取其中离平面最近的地面表面；
- 将平面上方落入同一格子的点视为顶棚候选，取其中离平面最近的上方表面。

最终每个切片、每个格子得到地面高程、顶棚高程及二者之间的间隔。若没有有效观测，相应表面标为无效。把点云对这些平面重复处理，便得到覆盖不同高度段的 tomogram。

这个表示并不要求建筑楼板恰好与切片平面对齐。论文指出切片间距需要足够小，才能覆盖机器人实际可通过的垂直空间；间距过大可能漏掉窄通道，过小则增加层数和计算量。

### 3.2 代码对应

仓库在 [`tomography/scripts/kernels.py`](../tomography/scripts/kernels.py) 生成点云投影、地面/顶棚和可通行性 CUDA kernel；[`tomography/scripts/tomogram.py`](../tomography/scripts/tomogram.py) 管理 GPU buffer、派发 kernel、层简化和导出。切片输出不是论文中的符号命名原样复刻，而是以 5 个数组通道保存，格式见[代码导读中的数据格式](./项目代码导读与调试手册.md#23-输出-pickle-数据格式)。

## 4. 可通行性：不只看地面，也看净空

对每个候选地面格，最基本的垂直净空是“顶棚高程减地面高程”。低于机器人最低需要空间的格子不可通行；在最低需要高度与正常行走高度之间，机器人可以通过降低身体高度适应，但应付出代价。这个思想使可调节高度的平台（例如四足机器人）可以在狭窄区域通过，同时避免把这种动作误认为毫无代价。

地面自身也要评估：局部高度差/坡度过大时可能无法站稳或跨越；局部邻域中若缺少足够平缓的支撑位置，则即使单格看似可过，也可能不安全。代码把净空、地面差分、邻域站立性合成代价，并把硬障碍赋予较大的屏障值。

随后用距离相关的膨胀权重把高代价向附近网格扩散。这不是对机器人几何外形的精确碰撞检测，而是给路径搜索和优化提供安全余量。机器人尺寸、定位误差和地图分辨率都应反映在膨胀与净空参数中。

## 5. 为什么要简化切片

若每个高度平面都保留，许多层的可行区域可能重复，搜索状态就会膨胀。论文的思路是删去不增加有效可达区域信息的冗余切片：如果某个切片的可行格已经被邻近切片覆盖，就不必再为它维护独立状态。简化应保留能表达新增地面、净空变化或跨层通道的层。

仓库在 `Tomogram.point2map()` 中使用地面高度差和代价图关系筛选保留索引。具体阈值/掩码以当前代码为准；修改该逻辑时要确保不会删掉坡道中间层、狭窄通道或真正连接上下层的格子。

## 6. Gateway 如何连接多层

单纯在每一层分别跑二维 A* 仍无法上下楼。gateway 的作用是在相同平面位置将相邻切片连接起来：当某个相邻层在该位置更能代表实际地面（例如代价更低且地面高度匹配），规划器可以从当前层转到另一层。沿坡道移动时，跨层转换与平面邻接交替出现，搜索由此覆盖三维结构。

仓库的 Python wrapper 根据相邻层的通行代价变化和地面高程接近程度构建 gateway 标记；C++ A* 的 `DecideLayer()` 查看当前层及相邻层标记来选择扩展层。它是一个局部连接机制，不是任意高度连续转换。若地图中坡道断开或层间路径找不到，应优先检查 gateway 图，而不是只调 A* 启发式。

## 7. 路径搜索与轨迹优化

### 7.1 分层网格上的 A*

A* 在简化后的切片网格上搜索。平面内采用 8 邻域，路径评分包括移动距离与可通行代价；启发式估计到目标的剩余网格距离。与在完整 3D 体素上搜索相比，状态数量较少，且每个状态关联了地面和顶棚等对地面机器人更有意义的信息。

搜索得到的是离散可行路径，并不保证轨迹已经平滑或动态可执行。代价阈值和 gateway 决定“哪些区域可走、哪些层之间能连”，优化器则处理曲率/速度连续性与障碍余量，两阶段不可互相替代。

### 7.2 GPMP 平滑

离散路径送入 GPMP 优化器后，连续轨迹由位置、速度等状态描述。优化图中包括起终点状态先验、相邻状态之间的高斯过程先验，以及节点和段间插值点的地图障碍因子。直觉上，GP 先验惩罚不平滑的变化，障碍因子把轨迹推离高代价区域，起终点先验则限制端点状态。

仓库提供两类状态模型：四维状态版本和六维状态版本；`use_quintic` 控制 wrapper 选择哪个优化器结果。轨迹水平位置由优化结果给出，地图层/地面与顶棚查询再参与高度处理。实际发布的 ROS `Path` 目前只包含位置，不包含内部速度，也没有输出执行器命令。

## 8. 论文报告的验证与结论

论文在多种模拟结构场景以及四足机器人真实环境中验证该框架，并与点云、网格或体素类规划方案比较。论文摘要报告的主要量级结果是：场景评估速度提高约三个数量级、路径规划速度约提升 3 倍，整体导航速度约提升两个数量级。它们是论文实验平台和对比配置下的结果，不应直接视为本仓库在任意 GPU、点云规模或机器人上的保证。

读论文实验部分时建议分开理解三项时间：

1. 点云预处理/地图构造；
2. 场景代价评估；
3. 路径搜索和轨迹优化。

地图分辨率、点云数量、切片间距和可行区域大小都会影响这些阶段，单看“总耗时”很难定位性能瓶颈。仓库 tomogram 生成器会对 GPU 模块重复运行并排除一次预热测量；规划端会打印 A* 与优化耗时，可用相同输入做对照。

## 10. 理解和调试时的边界条件

- 点云是离线建图输入；这份示例规划程序不会自动融合实时传感器数据或滚动更新地图。
- 切片本质上是离散近似。过大的切片间距可能遗漏狭窄可通行空间；过小会增大地图和搜索开销。
- 可通行性阈值依赖机器人能力。更换机器人后应重设净空、坡度、跨步、站立邻域与安全膨胀参数。
- 规划端示例把起终点切片索引固定为 0，且起终点 XY 坐标写在 `plan.py`；使用前确认其与 tomogram 的地图中心、frame 和单位一致。
- pickle 数组以 `float16` 存储，规划时再转 `float32`；NaN/哨兵值替换以及轴顺序是两端约定的一部分。
- 论文的性能数据用于说明方法效果，不是通用性能承诺。应在目标硬件和目标点云上分别测量建图、A* 与轨迹优化。
